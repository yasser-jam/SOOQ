Pillar 1 · Merchant Admin

Merchant Admin

The operational back office of a SOOQ store. Everything a merchant does that is not designing the storefront happens here: managing the catalogue, tracking stock, processing orders, arranging shipment and settlement, issuing invoices and refunds, and administering staff and store settings.

Application apps/web Routes 57 dashboard pages Modules 34 domain modules Audience merchant owner, manager, staff
How to read this document

Part A (§1–9) describes what the admin does, screen by screen — readable without opening the code. Part B (§10–15) explains how it is built. §16 is an exhaustive index of every route and module.

1The dashboard shell

The frame every admin page renders inside.

All merchant pages share one layout: a collapsible navigation sidebar pinned to the right edge — the document is dir="rtl" — a header carrying the store identity and the account menu, and the page body. The interface is entirely Arabic, set in Almarai, a typeface chosen for Arabic legibility at interface sizes.

Navigation structure

The sidebar groups every area of the product into seven labelled sections. Entries with sub-items are grouping headers — clicking one expands its children rather than navigating, so a group like “Logistics” organises pages without needing a landing page of its own.

GroupEntries
الرئيسية — HomeDashboard
الكتالوج — Catalogue Products (categories, tags, collections, custom attributes, import, import history), Inventory (low stock, bulk adjust)
المبيعات — Sales Orders, Logistics (shipping providers, shipments), Refunds
العملاء والتسويق — Customers & marketingCustomers, Discount codes
المالية — Finance Invoices (list, layout templates), Finance (COD settlement), Payment gateways
المتجر — StoreDesign Studio
الإدارة — AdministrationStaff, Settings (general, access control)

Two gates before any page renders

A merchant reaching a dashboard URL passes two checks. Middleware confirms a session token exists (§Overview 7). Then StoreConfigurationGate checks whether the store has actually been set up: immediately after first login the merchant holds a provisional tenant, and until they choose a public slug, name, and currency, every dashboard route redirects to the store-creation wizard.

Deliberate failure behaviour

The gate redirects only when the settings endpoint successfully reports an unconfigured store. A network or server error falls through and renders the dashboard rather than trapping the merchant in a redirect loop — an unreachable settings endpoint should not look like an unconfigured store.

2Access and onboarding

Getting into the dashboard, and what a new merchant sees first.

Signing in

Authentication is by one-time password sent to a phone number — appropriate for a market where phone identity is more reliable than email. The merchant enters a phone number, receives a code, and submits it; a resend cooldown prevents request flooding. Sign-in with a Google account is also supported as a second channel.

01Request code Phone submitted at /request-otp.
02Verify Code entered at /verify-otp; tokens issued.
03Gate Store configured? If not, the wizard.
04Dashboard Landing at the requested page, or home.

Creating a store

The wizard at /onboarding/create-store collects the minimum needed to make a tenant real: store name, a URL-safe public slug, category, and currency. The slug is validated against a strict pattern (lowercase words joined by hyphens) because it becomes part of the store's public identity.

Roles

The system recognises six roles. A user's roles arrive as a claim in their token and are re-checked by the backend on every request — the front end uses them only to decide what to show.

RoleMeaning
OWNERThe merchant who created the store. Full access, including settings and deletion.
MANAGERElevated staff — day-to-day operations across the dashboard.
STAFFStandard staff member. Capabilities are a fixed matrix defined by the backend.
CUSTOMERA storefront shopper. Never reaches the dashboard.
DRIVERDelivery role used by the shipping flow.
PLATFORM_ADMINOperator of the platform itself, across all tenants.
Design decision

Staff capabilities are a fixed matrix on the backend, not per-user permission strings stored and edited in the front end. An earlier design carried an editable permission list; it was removed. The admin now assigns a role and the backend decides what that role can do — one authority instead of two that can disagree.

Account security

Three self-service pages under /account let any signed-in user manage their own credentials, independently of their role:

  • Two-factor authentication — enrol an authenticator app by scanning a QR code, then enable or disable time-based one-time passwords.
  • Active sessions — list every session on the account and revoke any one individually, which is the remedy for a lost or shared device.
  • Phone number change — a two-step flow: request the change, then confirm it with a code sent to the new number, so the number cannot be changed without proving control of it.

3Catalogue

Products and everything that classifies them.

Products

The product editor is the largest single surface in the admin. It is organised as tabs so a merchant can save a usable product from the first tab alone and enrich it later:

TabContents
BasicsBilingual title and description, slug, status (draft / active / archived), base price, compare-at price, currency.
MediaImage upload, ordering, and removal.
CategorisationCategories, tags, and the default category. Both accept existing entries or new ones typed inline.
VariantsOption axes (e.g. size, colour) and the variant matrix they generate — per-variant SKU, price, cost, stock, barcode, weight.
AttributesCustom attribute values, driven by the attribute schema defined for the product's category.
InventoryStock quantities, low-stock thresholds, and whether overselling is allowed.
SEOSearch title and description, editable on their own page at /products/[id]/seo.

Two details in the product model are worth calling out because they shape the code as well as the experience. First, variants are derived, not enumerated by hand: the merchant defines option axes and their values, and the matrix of concrete variants follows. Second, classification accepts new entries inline — typing a category or tag that does not exist yet creates it on save, so cataloguing is not blocked by having to leave and set up taxonomy first.

Categories

Categories are hierarchical: each has children, forming a tree the merchant navigates and reorders. The platform ships category templates so a new store can adopt a ready-made structure for its sector instead of building one from nothing.

Tags

A flat, free-form labelling layer, independent of the category tree — the same product may carry any number of tags.

Collections

Collections are curated product groupings used for merchandising. They work two ways:

  • Manual — products added explicitly and reordered by hand, so the merchant controls exactly what appears and in what sequence.
  • Rule-based — conditions on product fields (a field key, an operator, a value) that select members automatically. Rules can be previewed and evaluated before saving, so the merchant sees what a rule captures before committing to it.

Custom attributes

Not every product type fits fixed columns — a shoe has a material, a phone has a storage size. Custom attributes let the merchant define their own fields and attach them to categories; the product editor then renders the right fields for whatever category a product belongs to.

Bulk import

Catalogues are usually migrated, not typed. The import flow is deliberately three-staged so a bad file cannot silently corrupt a catalogue:

01Upload Submit the file at /products/import.
02Preview Parsed rows and per-row errors shown before anything is written.
03Commit Accepted rows imported as a tracked batch.
04History Every batch kept with its status and row-level errors.

Import history at /products/import/batches is a permanent record: each batch keeps its status and the specific rows that failed, so a partial import can be diagnosed after the fact rather than guessed at.

4Inventory

Stock levels, and the operations that change them.

Stock is tracked per variant, not per product — a shirt is not in stock, a medium blue shirt is. Inventory has no list page of its own; it is reached either from a product (/products/[id]/inventory) or through two task-shaped pages:

PagePurpose
/inventory/low-stock Every variant at or below its low-stock threshold — the restocking work list.
/inventory/bulk-adjust Apply stock adjustments to many variants in one submission, for stock-takes and deliveries.

Adjustments are movements, not overwrites. Each change is recorded against the variant with a reason, and the movement history is retrievable per variant — so a discrepancy can be traced to the operation that caused it. Thresholds are set per variant, which is what makes the low-stock list meaningful across products of very different turnover.

5Orders and fulfilment

The order lifecycle, and the shipping operation that runs alongside it.

The order lifecycle

An order moves through a state machine. The admin does not offer free choice of status; at any moment the interface exposes only the transitions the current state permits, mirroring the state machine the backend enforces.

Three permission sets are derived from the current status and drive which buttons appear: cancellable (before anything has shipped), editable (before the order is committed to processing), and refundable (only once goods have reached the customer). Each is a separate concept — an order can be past the point of editing but still cancellable.

The order detail page

A single order gathers everything about it in one place: line items and totals, the customer's address, payment status and method, the linked shipment with its tracking state, internal notes visible only to staff, and an audit timeline recording who changed what and when. Four dedicated sub-pages handle the actions that need their own form — transition, cancel, edit, and returns.

Shipping

Fulfilment is modelled separately from the order, because a shipment has its own lifecycle and its own counterparties.

  • Shipping providers — the couriers a store works with, each configured with its own settings.
  • Shipments — the physical consignment. A shipment moves through its own status set (awaiting pickup → picked up → in transit → ready for office pickup → delivered, with failure and return outcomes) and keeps an event history.

Cash on delivery

Cash on delivery is the dominant payment method in the target market, and it creates a problem ordinary card payments do not: the courier collects money that then has to be handed back to the merchant. A COD shipment therefore carries a collection entry — the amount the courier took — and that entry has a settlement status of its own. Reconciling those entries is a finance task, covered in §6.

Refunds

Refunds are recorded against an order and listed centrally at /refunds. They can be raised only for orders that reached the customer, which is why refundable is a narrower set than cancellable — before delivery, the correct action is cancellation, not refund.

6Finance

Invoicing, settlement, and payment configuration.

Invoices

Invoices are generated from orders, never authored independently — the order is the source of truth and the invoice is its document. Generation and regeneration are actions on the order detail page; /invoices is a read-oriented list of what has been issued. Regeneration exists because an order can legitimately change after an invoice was first cut.

Invoice layout templates

Merchants need invoices that carry their own branding and show the fields their business requires. Layout profiles at /invoice-layouts control which fields appear on the document, so the same order data can be presented differently per store without changing the data.

COD reconciliation

The counterpart to COD collection. The merchant creates a reconciliation batch grouping the collection entries expected from a courier, then moves that batch through its settlement status as money actually arrives.

01Collect Courier takes cash on delivery; an entry is recorded per shipment.
02Batch Entries grouped into a reconciliation batch.
03Settle Batch marked settled — or disputed where amounts disagree.

The disputed state is the point of the feature: it gives a disagreement between the merchant's records and the courier's payment somewhere to live while it is resolved, instead of forcing a premature settled/unsettled decision.

Payment gateways

Payment provider configurations at /payment-providers determine how a store accepts money. The system currently recognises two payment methods: cash on delivery and the Paymera gateway.

7Customers and marketing

Who buys, and the incentives offered to them.

Customers

The customer list is the store's address book, with a detail page per customer. Two capabilities make it operational rather than merely informational:

  • Internal notes — staff-only annotations on a customer record, for the context that does not belong in an order (a delivery preference, a history of disputes).
  • CSV export — the customer list can be exported, so the data is not trapped inside the platform.

Discount codes

Codes that customers redeem at checkout, managed from /discount-codes with a detail page for creating and editing each one.

8Administration

Staff, store configuration, and the record of what was done.

Staff

Staff are invited by full name and phone number — the same phone identity the login flow uses, so an invited member signs in exactly as the owner does. Access control lives on its own page at /settings/access, separate from staff records, because assigning capability is a different decision from recording who someone is.

Store settings

Settings are the largest form in the application, split into eight tabs. It is a single form over a single record, not eight independent forms — which matters for how saving works (§13).

TabControls
IdentityStore name and public slug.
GeneralCore store details and contact information.
AddressPhysical address, including map pin selection.
BrandingLogo and brand assets.
Currency & displayCurrency, symbol position (before or after the amount), and numeral system — Arabic or Latin digits.
Social linksLinks to the store's social presence.
Business hoursOpening hours per day of the week.
Danger zoneStore deletion request.
Localisation is configuration, not code

Symbol position and numeral system are per-store settings rather than fixed behaviour. A store may display ١٢٥٠٠ ل.س or SYP 12,500 from the same underlying number — the presentation belongs to the merchant, not the platform.

Audit log

/audit-logs is the store-wide record of security-relevant events. It complements the per-order timeline: the order timeline answers “what happened to this order”, the audit log answers “what has been done in this store”.

9Platform surface

The operator's view, across all tenants.

One area of the application serves the platform operator rather than any merchant. Under /platform, a holder of PLATFORM_ADMIN can list every tenant on the platform and disable one. Related controls exist for a tenant's status and rate limits.

Scope

The platform surface is deliberately minimal — tenant listing and disabling, no billing, plan management, or cross-tenant analytics. It exists to demonstrate that the multi-tenant model has an operator dimension, not as a finished operations console. An apps/platform-admin workspace directory exists but contains no application; the platform pages currently live inside apps/web.

10Application structure

How the Next.js application is laid out, and what wraps every page.

Route groups

Directories in parentheses group routes without contributing a URL segment. Each group carries its own layout, which is how one application serves audiences with entirely different chrome.

GroupURLsLayout
(dashboard)/, /products, … Full shell — sidebar, header, providers, configuration gate.
(auth)/request-otp, /verify-otp Bare, centred authentication layout.
(platform)/platform/…Platform-operator pages.
—/onboarding/create-store, /welcome Standalone pages outside any group.
Also present in apps/web

The published-store and shop trees also live under apps/web/app. They are not part of the admin — they are the customer storefront, documented in the Renderer document, and belong in apps/store. Their presence here is the temporary duplication described in the overview.

The provider stack

Every dashboard page is wrapped by one client component that composes the application's cross-cutting concerns. Order matters — each layer depends on the one outside it.

Two decisions in this file are worth explaining:

  • DirectionProvider dir="rtl" tells every Radix primitive that the document is right-to-left, so dropdowns, popovers, and sliders resolve “start” and “end” correctly. Without it, RTL layout would have to be patched component by component.
  • The sidebar reads store settings through the same query the settings page uses. Because they share a cache key, saving settings in one tab refreshes the store name in the sidebar without any explicit wiring between them.

The query client is created with useState rather than at module scope — one client per browser session, never shared across users during server rendering — and configured with a 30-second freshness window and a single retry.

11The domain module pattern

The organising idea of the codebase, and the reason 34 features look alike.

Business logic does not live in route files. Routes are thin; each feature lives in a domain module under apps/web/modules/<domain>/<name>, and every module repeats the same small set of files. The payoff is that learning one module teaches all of them, and adding a feature is copying a shape rather than inventing one.

FileResponsibility
schema.tsZod schemas. The single source of truth for both validation and types.
types.tsAPI request/response shapes, mostly inferred from the schemas.
actions.tsEvery API call for the domain, plus the normalize* mappers between wire and form shapes.
queryKeys.tsThe cache key factory — the vocabulary for reading and invalidating cached data.
init.tsBuilds form default values. One initialiser shared by create and edit.
components/UI owned by the module — its table, its cards, its dialogs, its editor tabs.
hooks/Module-specific hooks, where a feature needs stateful behaviour of its own.
model.ts / helpers.tsPure domain logic, where there is any — the order state machine lives here.

How a request flows

01Route Thin page renders the module's component.
02Query Component calls useQuery with the module's key + action.
03Action Action calls the API client, unwraps the envelope, normalises the shape.
04Form init.ts turns the entity into defaults; the schema validates edits.
05Mutate On success: invalidate the key, toast in Arabic, navigate back.
Deliberately no repository layer

useQuery and useMutation are called inside the page or detail component, using the module's own actions and keys. There is no intermediate “service” or custom hook wrapping every entity. For a dashboard that is overwhelmingly list → detail → save, an extra abstraction layer would add indirection without removing duplication.

Worked example — the product module

modules/product/product is the largest module (25 files) and exercises every part of the pattern. Following it end to end shows how the pieces fit.

1 — The cache key factory

Because detail is built by spreading all, invalidating productKeys.all after a mutation also invalidates every product detail — the list and the item the merchant just edited both refresh from one call. Every module defines this same two-line shape.

2 — The schema as the source of truth

Three things are visible here. Validation messages are Arabic, because they are shown to the user unmodified. Bilingual fields appear as *Ar / *En pairs throughout. And refine encodes a rule no single field can express — a category reference is valid if it has either an identifier or a name, which is exactly what makes inline creation possible.

3 — One initialiser for create and edit

The optional parameter is the whole trick: called with no argument it yields create defaults, called with an entity it yields edit defaults. Create and edit therefore cannot drift apart, because there is only one definition of what a blank field means.

4 — Actions: unwrap, normalise, submit

12Data layer

One HTTP client, one envelope, one set of conventions for the awkward cases.

The API client

A single axios instance in lib/api.ts serves the whole application. Its request interceptor is where authentication and tenancy are applied, so no calling code ever thinks about either:

A small but load-bearing detail

The instance deliberately sets no default Content-Type. Axios infers it per request body — JSON for plain objects, multipart with the correct boundary for FormData. Setting a default would break every file upload in the application, including the product editor.

Single-flight token refresh

A dashboard page typically issues several requests at once. If the access token has expired, all of them fail together — and a naive implementation would fire several refresh calls, most of which are invalidated by the first. The client holds one shared promise instead:

Concurrent failures await the same refresh; each original request is retried once, marked by a _retry flag so a genuinely dead session ends in logout rather than an infinite loop.

Unwrapping the envelope

Every response arrives wrapped (§Overview 8). Actions unwrap .data and read pagination from meta, so components never see the envelope. Errors are handled centrally: errorCode maps to an Arabic message through lib/error-codes.ts, and fieldErrors is applied onto the form so server-side validation appears next to the offending input, exactly like client-side validation.

Normalisation

Backend shapes and form shapes are not the same, and pretending otherwise leaks API structure into components. Each module keeps explicit mappers — normalizeGetProduct, for instance, flattens the response's variantMatrix.options[] into the flat options array the form expects. The rule is that the translation happens once, in actions.ts, and nowhere else.

Media semantics

Editing images needs to express three different intentions, and a plain array cannot. The repo-wide convention on mediaAssetIds is:

ValueMeaning
nullLeave existing media untouched. The default when opening an edit form.
[]Clear all media. An explicit instruction, distinguishable from “unchanged”.
[ids]This exact list, in this order.

Newly selected files travel separately as multipart files parts in the same request. Without the tri-state, opening a product and saving it without touching the images would be indistinguishable from deleting them all.

Client-side authorisation is presentation only

Role checks in the front end decide what to render. The RequireRole component reads the current user's roles and renders a fallback — or a not-found page — when they do not match. The JWT helper that reads token claims is explicit about the boundary:

Hiding a button is a usability measure, not a security control. Every request is authorised again on the server.

Running without a backend

A mock layer under lib/mock intercepts requests before they leave the client when NEXT_PUBLIC_USE_MOCK_API is set, serving seeded data for authentication, onboarding, catalogue, discount codes, and shipping. Some modules additionally keep local-storage fallbacks used only in this mode. It exists so the interface can be developed and demonstrated against a backend that is unavailable or incomplete.

13Forms and validation

Zod schemas, react-hook-form, and the patterns that keep large forms manageable.

Schema first

A Zod schema is written once and used three ways: it validates input, it produces the TypeScript type through z.infer, and it carries the Arabic error messages shown to the user. There is no separate interface to keep in step with the validator, because the validator is the type.

Forms use react-hook-form with zodResolver. The uncontrolled approach matters at the scale of the product editor: a form with a large variant matrix does not re-render the whole tree on every keystroke.

Input versus output types

Several modules distinguish z.input from z.output — the shape the form holds before coercion versus after. A numeric field is a string while the user is typing and a number once parsed; keeping both types explicit prevents the form state and the payload type from being conflated.

Saving only what changed

Store settings is one form over eight tabs, and sending the entire settings object on every save would overwrite fields another session may have changed. The module therefore pairs its initialiser with a diffSettingsPayload function and submits only modified fields. The pattern generalises: build defaults from the entity, diff against them on submit.

Detail-page pattern

Create and edit share one page component per entity, distinguished by whether a record was loaded. Both call the same init.ts, both validate with the same schema, and both finish the same way — invalidate the module's query key, show an Arabic toast, navigate back to the list. Consistency here is what makes 34 modules feel like one application.

14Server state

Caching, invalidation, and why there is almost no client state.

Nearly everything the admin displays belongs to the server. TanStack Query manages it directly, which means the application keeps very little state of its own: no store of products, no duplicated order list, no manual refresh logic. The defaults are set once on the client — data stays fresh for 30 seconds and a failed request is retried once — and the query key is the unit of coordination.

The invalidation contract

Every mutation ends the same way:

  1. Invalidate the module's root key, e.g. queryClient.invalidateQueries({ queryKey: productKeys.all }).
  2. Show an Arabic success toast through sonner.
  3. Navigate back to the list.

Because detail keys are built by extending the root key, invalidating the root refreshes the list and every open detail at once. This is the whole reason for the key-factory convention in §11.

Shared queries as implicit wiring

Two components that call the same query with the same key are automatically consistent. The sidebar and the settings page both read store settings; saving in one updates the other with no code connecting them. Used deliberately, this replaces a good deal of state-management machinery.

15UI layer

The design system, the shared building blocks, and the conventions that keep pages uniform.

Two layers of components

LayerLocationContents
Design systempackages/ui/src/components 37 primitives — button, table, dialog, popover, sidebar, tabs, skeleton, pagination. Vendored shadcn-style components, editable at source.
System componentsapps/web/components/system 19 composed, application-aware widgets — DataTable, FilterMenu, EmptyState, image uploader, phone field, map pin picker, confirm alert, creatable select.

The distinction is intent: packages/ui knows nothing about commerce, while components/system encodes decisions specific to this admin — how a table paginates, what an empty list should say, how a phone number is entered.

DataTable

Every list in the admin renders through one component built on TanStack Table, which is why pagination, sorting, loading skeletons, expandable sub-rows, and empty states behave identically across 30-odd screens. An empty list is never a blank rectangle: the table takes an emptyState node and renders it as a full-width row, so each list can explain its own emptiness.

Page conventions

List pages follow a fixed anatomy — page title, a FilterMenu popover, and a system-styled action button. The conventions are enforced by house rules rather than by types:

  • No raw <button> elements and no hard-coded colour values — always the design-system Button and theme tokens.
  • List routes stay thin; the module owns the table component.
  • User-facing strings are Arabic; identifiers, file names, and comments are English.
  • Files are kebab-case; components are named exports rather than default exports.

Theming and RTL

Colour, radius, and spacing come from CSS custom properties defined once in packages/ui/src/styles/globals.css — navy #122640 as primary, gold #BA7B1B as secondary. Right-to-left is handled at the root (dir="rtl" on the document, DirectionProvider for primitives) rather than per component, and the sidebar is anchored to the right accordingly.
