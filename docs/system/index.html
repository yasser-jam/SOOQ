Pillar 0 · Overview

SOOQ — System Documentation

SOOQ is a multi-tenant e-commerce platform: it lets a merchant create an online store, manage its catalogue and operations from an administrative dashboard, and design the public storefront visually without writing code. This document set is the reference for the implemented web platform — what it does, and how it is built.

Scope implemented web platform Branch stage Repository SOOQ — pnpm + Turborepo monorepo Last updated 2026-08-13

1What SOOQ is

The problem the platform solves, and the shape of the solution.

The problem

A merchant who wants to sell online has two bad options. Building a store from scratch demands development skills and months of work. Using a generic website builder produces a site that looks like a store but has no commerce engine behind it — no inventory, no order lifecycle, no shipping or settlement.

SOOQ closes that gap. One merchant signs up, gets an isolated tenant, and receives both halves at once: a complete operational back office, and a visual builder that produces the customer-facing storefront. The platform is Arabic-first — the entire interface is Arabic with a right-to-left layout, and content entities carry parallel Arabic and English fields.

Product shape

Model
Multi-tenant SaaS — one deployment serves many independent stores, isolated by tenant.
Merchant surface
A dashboard covering catalogue, inventory, orders, fulfilment, finance, customers, and staff.
Customer surface
A published storefront whose pages are designed by the merchant, not hard-coded by us.
Localisation
Arabic UI, RTL layout, *Ar / *En bilingual data fields, default currency SYP.
Backend
An external Spring REST service. This repository is the entire front-end platform.
Scope of this document

This covers the web platform in this repository. The backend service is described only through the contract it exposes (endpoints, envelope, headers) — its internal implementation is out of scope. A mobile client is not part of the current system.

2The three pillars

The system divides into three subsystems. Each has its own document in this set.

PILLAR 1

Merchant Admin

The operational back office. A Next.js application built on a shadcn-style design system, organised into domain modules — products, orders, shipping, finance, customers, staff.

apps/web · 57 dashboard pages
PILLAR 2

Design Studio

The visual page builder. A customised fork of the Puck editor with a purpose-built block library, letting merchants compose storefront pages by dragging blocks onto a canvas.

@puckeditor/core · 60 blocks
PILLAR 3

Template Renderer

The published storefront. Reads the same design document the editor produces and renders it for customers, wired to live catalogue, cart, and order data.

apps/store · port 3001

How they relate

The admin and the editor are two areas of the same application: the Design Studio is reached from the dashboard sidebar and runs inside apps/web. The renderer is a separate application, apps/store, serving customers rather than merchants. Editor and renderer are nonetheless two modes of the same code — they share one block library and one configuration; the editor mounts it in an editable canvas, the renderer mounts it read-only. That is why this document set treats them as a single subsystem viewed from two sides, even though they ship as different applications.

The artefact that ties them together is the Site JSON — a serialisable document holding the store's theme, its shared shell zones (header, footer, drawers), and its pages. The editor writes it; the renderer reads it. Neither knows anything else about the other.

01Merchant designs Drags blocks onto the canvas in Design Studio.
02Site JSON Theme + zones + pages serialised to one document.
03Renderer reads Storefront resolves the page and renders its blocks.
04Blocks bind data Product, cart, and order blocks fetch live tenant data.

3System architecture

The layers, and what depends on what.

Reading the diagram

  • Two applications, split by audience. apps/web serves merchants — the admin dashboard and the editor. apps/store serves customers — the published storefront. They deploy independently and can be scaled independently.
  • One handoff. The only thing crossing from editor to renderer is the Site JSON. There is no shared runtime state between them.
  • Downward dependency only. Applications import from the shared layer; the shared layer never imports from an application — with one documented exception described in §4.
Temporary implementation note

The architecture above is the intended and documented design: the storefront is apps/store, its own application. At the time of writing, the working implementation of the storefront in fact lives inside apps/web, under a published-store route tree that apps/web's middleware rewrites /store/[tenantId] onto.

This duplication is temporary and exists only to keep the storefront and the admin's modules moving together during development. The storefront is to be moved wholesale into apps/store, after which apps/web will serve merchants only. Nothing in the design depends on the current arrangement — the rest of this document set describes the storefront as the separate application it is meant to be.

Path aliases

Aliases are what make the cross-package structure ergonomic. Three matter:

AliasResolves toUsed by
@/core, @/core/* packages/editor-packages/core apps/web, apps/store
@workspace/ui/* packages/ui/src/* apps/web
@/modules/*, @/lib/*, @/config/* apps/web/modules, apps/web/lib, apps/web/config apps/store — resolves into apps/web
Known coupling

The last row is a deliberate but risky shortcut: apps/store aliases @/modules and @/lib into apps/web, so the storefront reuses the admin's domain modules and API client instead of duplicating them. The benefit is a single source of truth for API calls; the cost is that moving a file inside apps/web/lib or apps/web/modules can break a different application. This is examined further in the Renderer document.

6Audiences and routing

Three audiences, separated by route namespace: merchants, the platform owner, and customers.

The first two are served by apps/web; customers are served by the storefront application. Within apps/web, route groups — the parenthesised directories under app/ — split the application by audience without appearing in the URL. Each group has its own layout and its own access rule.

These two namespaces belong to the customer-facing application and are documented in full in the Template Renderer document. They are listed here because both are currently served from apps/web — see the temporary implementation note.

Correction to earlier project notes

Merchant pages were originally addressed as /store/[storeSlug]/…. They are not any more. Merchant routes now sit at the root and the tenant is resolved from the session, while /store/[uuid] means the published storefront. Old merchant links still work: middleware.ts issues a permanent redirect from /store/{slug}/x to /x. The repository's CLAUDE.md still describes the old scheme and should be corrected.

What middleware decides

A single middleware runs before every request and resolves three questions in order:

01Storefront? If the path is /store/<uuid>, hand it to the storefront route tree and stop — no authentication is required.
02Legacy link? If /store/<slug> — a non-UUID segment — redirect permanently to the equivalent root path.
03Authenticated? Public prefixes pass through. Otherwise require a token; if none, redirect to login carrying the original path.

The distinction in the first two steps is made by testing the segment against a UUID pattern: a UUID means a tenant's storefront, anything else means a legacy merchant slug.

7Multi-tenancy and authentication

How a request is attributed to a store and a user.

Two independent sessions

A merchant signing into the dashboard and a customer signing into a storefront are different identities that may exist in the same browser at the same time. The system therefore keeps two separate token cookies and picks between them per request.

CookieHoldsNotes
sooq-admin-access-tokenMerchant / platform JWTUsed for admin endpoints.
sooq-store-access-tokenStorefront customer JWTUsed for /customer/** endpoints.
sooq-refresh-tokenRefresh tokenhttpOnly — unreadable from JavaScript.
sooq-tenant-slugStore slugHuman-readable tenant key for merchant requests.
sooq-tenant-idTenant UUIDMachine tenant key for public storefront requests.
sooq-user-nameDisplay nameConvenience only, not an authorisation input.

Token selection is by endpoint: a request whose URL contains /customer/ is signed with the customer token, everything else with the admin token. Only the refresh token is httpOnly, because the access tokens must be readable by the client-side HTTP interceptor that attaches them.

Tenant resolution

The backend needs to know which store a request concerns. Two headers carry that, depending on the surface:

X-Tenant-Slug
Merchant requests. The slug is stored client-side and attached automatically to every admin call by the request interceptor.
X-Tenant-Id
Public storefront requests, where there may be no session at all. The tenant UUID comes from the URL segment, a cookie, or — when a customer is signed in — from a claim inside their token.
Why two keys

The slug is what a merchant recognises and what appears in their links; the UUID is what an anonymous storefront visitor can be given safely in a URL without leaking a guessable store name. Both identify the same tenant.

Silent refresh

Access tokens expire during normal use. Rather than interrupting the merchant, the HTTP client handles it transparently: a 401 triggers a refresh, and the original request is retried with the new token. Concurrent failures share a single in-flight refresh — a common source of duplicate-refresh bugs — and each request is retried only once, so a genuinely invalid session ends in logout rather than a loop.

Middleware deliberately does not validate tokens. It only checks that some token is present, letting the page render and leaving genuine expiry to the refresh mechanism. Only when both the access and refresh tokens are absent does it redirect to login.

8The API contract

One envelope shape, used by every endpoint.

The backend is reached at NEXT_PUBLIC_API_URL, which must end in /api/v1. Administrative endpoints are prefixed /admin/…, customer endpoints /customer/…. Every response — success or failure — arrives inside a uniform envelope, so the client has exactly one unwrapping rule.

Three consequences shape the whole data layer:

  • Payloads are always unwrapped from .data, and list pagination always read from meta — never from the array itself.
  • Errors are structured. errorCode maps to a translated Arabic message, and fieldErrors maps server-side validation failures onto individual form fields, so backend validation surfaces in the same place as client-side validation.
  • Backend shapes are not form shapes. Each module keeps explicit normalize* mappers translating between the two, rather than letting API shapes leak into components. This is detailed in the Admin document.
Development without a backend

The front end can run against an in-repository mock layer instead of the live service, toggled by NEXT_PUBLIC_USE_MOCK_API. It intercepts requests before they leave the HTTP client and serves seeded data for authentication, onboarding, catalogue, discount codes, and shipping. Several modules additionally keep local-storage fallbacks used only in that mode.

9How to read this document

Structure, conventions, and where to start.

Structure

Each pillar document is split into a functional half — what the subsystem does, written for a reader who will not open the code — and an implementation half, which explains how it is built and ends with a file-level reference map. A reader evaluating the product can stop after the functional half; a reader extending the code should read both.

Known limitation, recorded deliberately rather than omitted.
On gaps

Limitations are documented, not hidden. Where the implementation is provisional — the Site JSON persistence layer being the most significant example — this document says so and explains the consequence. An honest account of the boundary is more useful than a claim of completeness.

Callouts

Blue callouts add context or rationale. Amber ones record a gap or a deliberate trade-off. Red ones flag something that is wrong, out of date, or actively risky. Green ones confirm a guarantee the system provides.
