The drag-and-drop freeze — root cause found

dnd-kit 0.1.18 completes a drop through one un-guarded promise chain with no .catch and no timeout (@dnd-kit/dom/index.js:901). If that promise rejects or throws, the drag source is stranded at status "dropping" forever. Every downstream consumer then wedges: the Cursor plugin's injected * { cursor: grabbing !important } stylesheet is never removed (the closed-hand cursor you see), actions.start() throws on every subsequent drag, and stop() early-returns on its aborted controller so nothing can recover it short of a page reload. Puck's own onDragEnd waits on the same never-arriving signal, so ui.isDragging also stays true.

Fixed in this pass with a watchdog + forced recovery (§12.3), plus a leaked-effect fix in the same handler that was accumulating stale dispatch callbacks over a long session.

Bilingual content — canvas crashes fixed; migration still incomplete

User-facing text props are moving from plain string to BilingualString = { ar, en }. normalizeEditorData rewrites saved Site JSON on read via BILINGUAL_PROPS (18 block types + root). The runtime crashes that were taking down Design Studio on load are fixed in this pass:

  • Puck chrome Header resolves root.title with pickLang()
  • Testimonials fully converted (fields + sample data + render)
  • Zone overlay blocks renamed reserved React prop key → zoneKey (with a read-time rename migration)

Still broken / unfinished if those blocks appear on a page: Accordion, ButtonGroup, ContactForm.submitLabel, SiteHeader/SiteFooter/SiteDrawerShell (still on the sibling *Ar helpers while migration collapses them into bilingual objects). Full status in §6.1; remaining work in §16, Phase G.

Related: the root-level migration is not idempotent — defaults are merged after the bilingual pass, so drawerTitle, drawerTriggerLabel and footerTagline stay strings on the first normalise and become { ar, en } on the second. Several site-data / mobile-sync specs currently fail because they expect bare strings. §13.9

The three structural problems behind everything else

  1. The barrel cycle. components/AutoField/.../ArrayField imports from the package's own public barrel (bundle/index.ts), which re-exports config/index.tsx, which eagerly imports all 62 blocks. Editing one block recompiles the entire editor. §14.1
  2. Type checking is off. Both Next configs set typescript.ignoreBuildErrors: true, and the fork's own tsconfig.json cannot resolve its own aliases. 648 type errors are currently invisible. §13.1
  3. 16 files are byte-identical duplicates between apps/store and apps/web/modules/storefront. §15.3

Persistence is still localStorage-only

site-data.ts reads and writes window.localStorage directly (site-data.ts:485, :528, :553). There is no backend write path — a merchant switching device or clearing site data loses the whole storefront design. apps/web/modules/design-studio/draft.ts exists and calls saveWebDesignDraft, so the seam is there; the read path has not been moved. Tracked in §16, Phase F.

The normalise pipeline

Every read and every save funnels through config/lib/normalize-editor-data.ts (836 LOC). It is the only place old payloads get upgraded, and it runs on the whole tree, so order matters. Per node, normalizeComponentNode() applies:

1 migrateRenamedProps(type, props) RENAMED_PROPS — e.g. ZoneDrawer.key → zoneKey 2 migrateBilingualTextProps(type, …) BILINGUAL_PROPS — "text" → { ar, en }, collapsing any sibling *Ar prop 3 mergeDefaults(config defaults, …) fills in anything the payload omits 4 stripVisualOnlyKeys() drops __-prefixed editor-only keys 5 normalizeNestedComponents() recurse into slots / arrays 6 ensure a stable props.id

Root props take the same path plus migrateLegacyShellLinks() and the shellComponentsMigrationVersion gate (currently 4), which decides whether missing shell blocks get inserted. Two registries drive the per-type behaviour and both are plain data, deliberately importing nothing from blocks so they cannot create cycles: config/lib/bilingual-props.ts and the RENAMED_PROPS map inside normalize-editor-data.ts.

Note the ordering bug in step 2 vs 3: defaults are merged after the bilingual pass, so a prop supplied only by defaultProps is not migrated on the first run. §13.9

Editor modes (desktop / mobile)

config/lib/editor-mode.ts + mobile-sync.ts implement a second SiteData instance under the :site:mobile key. The host picks EDITOR_METADATA_DESKTOP or EDITOR_METADATA_MOBILE — these are module-level constants specifically because changing the metadata identity rebuilds the whole Puck store (design-studio/[...puckPath]/client.tsx:78-90). Keep them stable.

The lifecycle

onBeforeDragStart dragMode = "new" | "existing" zoneStore.draggedItem = source ui.isDragging = true [data-puck-entry] gets data-puck-dragging → CSS shows drop targets onDragStart seed previewIndex[sourceZone] with a "move" preview onDragOver (×N) event.preventDefault() ← suppresses dnd-kit's own reordering compute targetZone/targetIndex from collision direction + RTL dir write previewIndex → DropZone re-renders with a ghost at the target pointermove (×N) NestedDroppablePlugin → onChange → zoneStore.zoneDepthIndex (debounced 100 ms; fallback collisions disabled for 100 ms after a switch) onDragEnd ▶ WAIT for source.status === "idle" ◀── THE FREEZE POINT then: insertComponent() | dispatch("move") ui.isDragging = false remove data-puck-dragging

Note the deliberate inversion: Puck suppresses dnd-kit's optimistic reordering (event.preventDefault() in onDragOver) and instead maintains its own previewIndex, applying the real mutation only once the drop animation has finished. That is why a stalled animation doesn't just look wrong — it loses the edit entirely.

Block contract

Every block must render safely in three contexts: the editor iframe, the client <Render>, and RSC. Practically that means: no window at module scope, all browser work behind useEffect, and a *Client.tsx split when the block needs state (see CategoryListMenu/CategoryListMenuClient.tsx for the pattern).

6.1 Bilingual content

SOOQ is Arabic-first. Merchant-authored copy is stored as BilingualString = { ar: string; en: string } (DSN-016 / OTA: plain JSON, no functions). Helpers live in lib/bilingual.ts (normalizeBilingual, pickLang); the reusable Puck field is config/fields/BilingualText (bilingualTextField()). Active language comes from config/locale/LanguageContext + LanguageProvider, which Root mounts when nothing higher in the tree has already provided one.

Contract for every bilingual prop

  1. Register the path in config/lib/bilingual-props.ts (collapseFrom when a legacy *Ar sibling exists).
  2. Expose it with bilingualTextField({ label, mode? }) — not type: "text".
  3. Default to a full { ar, en } object (never a bare string).
  4. Resolve at render with pickLang(value, language) before any JSX child / attribute / .trim() / string concat.

On every read/save, normalizeComponentNode runs migrateBilingualTextProps (see §3). Legacy payloads with a plain string (or a pair of name + nameAr) become { ar, en }; already-migrated objects are left alone.

8. Binding & the data adapter

config/binding/ (useBoundData, useBoundValue) lets a block prop point at live product/collection data instead of a literal. It is fully spec-covered and imports nothing from apps/web — a test enforces that boundary. Keep it.

config/data-adapter/ defines the EditorDataAdapter interface and ships a sample catalogue. apps/web/lib/editor-data-adapter.ts registers the axios-backed implementation at startup. The edit canvas always renders instant sample data (no network); preview and the storefront fetch live. That asymmetry is deliberate — do not "fix" it by making the canvas fetch.

9. Shell zones & pages

config/shell-zones.ts defines SITE_ZONE_KEYS; the zone blocks (ZoneDrawer, ZonePopup, ZoneBottomSheet, SiteHeader, SiteFooter) render into SiteData.zones rather than page content, so they persist across pages. config/lib/zone-events.ts (openZone/closeZone/toggleZone) and zone-registry.ts wire runtime open/close.

Zone event key is zoneKey, not key

Overlay zone blocks used to store their event-bus id under the prop name key. Spreading that props object into JSX (MemoizeComponent → <Component {…renderProps} />) made React treat it as the React key and warn "A props object containing a 'key' prop is being spread into JSX" — the block never actually received the value.

Renamed to zoneKey on ZoneDrawer / ZonePopup / ZoneBottomSheet (fields, defaults, presets, theme JSON, ZonesPanel). RENAMED_PROPS in normalize-editor-data.ts rewrites legacy key → zoneKey on read so saved storefronts keep working. Match this value from sooq:zone events / data-sooq-zone-toggle.

config/page-registry.ts holds the built-in page definitions and dispatches PAGES_UPDATED_EVENT; config/pages.ts handles custom pages. Route patterns support dynamic segments (/products/:product-slug) resolved by findSitePage.

10. Theme & settings

config/theme.ts (863 LOC) defines FullThemeProps — colours, typography, spacing scale, button variants, badges, shell. config/theme-presets.ts (500 LOC) ships ready-made themes. settings/ThemeInjector.tsx serialises the active theme into CSS custom properties and injects them into the canvas iframe document; the storefront does the same at render time via PreviewThemeProvider.

Custom field types under config/fields/ (BilingualText, ThemeColorField, SpacingField, BorderField, LinkField, ProductPickerField, CollectionPickerField…) are what make the right sidebar feel bespoke rather than generic Puck. For merchant copy, prefer bilingualTextField() over type: "text" (§6.1).

12. The drag-and-drop freeze

Symptom

After working in the editor for a while, drag and drop stops responding and the cursor is stuck as a closed hand (grabbing) everywhere on the page — including over text and sidebars. Only a reload fixes it.

Why "cursor stuck grabbing" is a precise diagnostic, not a vague symptom

dnd-kit's Cursor plugin does exactly one thing (@dnd-kit/dom/index.js:299-321): while dragOperation.status.initialized is true, it appends <style>* { cursor: grabbing !important; }</style> to the document head, and removes it when that flips false. A permanently-grabbing cursor therefore means one thing and only one thing: status.initialized never went back to false. initialized is value !== "idle" && value !== "initialization-pending" — so the operation is stranded mid-flight.

12.1 The failure chain

Tracing backwards from a stranded operation, through @dnd-kit/abstract and @dnd-kit/dom 0.1.18:

// @dnd-kit/dom — Feedback plugin, drop animation (index.js:~901)
animateTransform({ element: feedbackElement, keyframes, options })
  .then(() => {
    feedbackElement.removeAttribute(DROPPING_ATTRIBUTE);
    animation?.finish();     // ← CAN THROW: InvalidStateError on an
                             //   infinite / unresolved-duration animation
    onComplete?.();          // ← the ONLY thing that sets source.status = "idle"
    requestAnimationFrame(restoreFocus);
  });
  // no .catch — no timeout — no fallback

// where animateTransform is literally:
function animateTransform({element, keyframes, options}) {
  return element.animate(keyframes, options).finished;   // ← rejects on cancel()
}

If that promise rejects or the body throws, this cascade follows:

#WhereWhat stays wrong
1Feedback plugin cleanup()Never runs. source.status stays "dropping". The real element keeps [data-dnd-dragging], position: fixed, popover top-layer promotion and --dnd-* vars — glued to the cursor. Its clone [data-dnd-placeholder] stays in the layout flow.
2abstract/index.js:816-836stop() is waiting inside effect(() => { if (source.status === "idle") cleanup() }). That effect never fires, so dragOperation.reset() never runs and status stays "dropped".
3Cursor pluginstatus.initialized is still true → the * { cursor: grabbing !important } stylesheet is never removed. This is the visible symptom.
4abstract/index.js:699actions.start() now throws "Cannot start a drag operation while another is active" on every subsequent drag attempt. Look for this in the console — it confirms the diagnosis.
5abstract/index.js:798stop() early-returns on controller.signal.aborted. So Escape, blur, clicking, manager.destroy() — nothing can recover it.
6DragDropContext.onDragEndPuck waits on the same source.status === "idle" signal, so onAnimationEnd() never runs: the dropped block is never inserted/moved, previewIndex is never cleared, and ui.isDragging stays true — which keeps every DropZone in "drop target" styling.

12.2 What makes the promise fail — and why it gets likelier over a session

Three independent paths, all reachable in this codebase:

  1. animation.finish() throws. getFinalKeyframe() picks up any running animation on the dragged element whose keyframes contain translate, pauses it, then calls .finish() on it inside the .then. Animation.finish() raises InvalidStateError when the effect has an infinite or unresolved end time. The editor ships several … infinite CSS animations (ProductsGridTemplateRepeater.tsx:56, ProductsPageTemplateRepeater.tsx:39, SiteDrawer/styles.module.css:237, Loader/styles.module.css:19).
  2. The WAAPI animation is cancelled. .finished rejects with AbortError if the animation is cancelled — which happens when the element is detached or replaced mid-drop. The 250 ms drop window is exactly when Puck's React tree is churning hardest.
  3. The iframe re-creates its document. The feedback element usually lives in the canvas iframe; an AutoFrame remount during the drop cancels everything in it.

Two SOOQ-side amplifiers make (2) far more likely the longer a session runs:

A per-frame requestAnimationFrame loop that re-renders during the drop. DraggableComponent/index.tsx:384-409, 664-668 — while a block's overlay is visible, watchPosition() polls getBoundingClientRect() every frame and calls sync() → setState whenever the element moved. During a drop animation the element moves every single frame, so this fires a React state update ~60×/s into the exact subtree that owns the animating element.

Nested timeouts that re-render just after the drop. DropZone/lib/use-min-empty-height.ts:47-70 — a 100 ms timeout that calls node.methods.sync() on every sibling, nesting a further 200 ms timeout for the selected item. Both land inside the 250 ms animation window.

And a third factor explains "after working for some time" specifically — a leaked subscription in Puck's own handler: 

// BEFORE — components/DragDropContext/index.tsx
let dispose: () => void | undefined;

dispose = effect(() => {              // @dnd-kit/state effect() runs its body
  if (source.status === "idle") {     // SYNCHRONOUSLY on creation
    onAnimationEnd();
    dispose?.();                      // ← `dispose` is still `undefined` here
  }                                   //   on that first synchronous run
});

Whenever source.status is already "idle" at dragend (a cancelled drag, a zero-distance drop), the effect fires immediately, dispose?.() no-ops, and the subscription is never released. It stays live for the rest of the session and re-runs onAnimationEnd() — with its stale captured thisPreview, initialSelector and dragListeners — on every later status change of that draggable. These accumulate one per affected drag, producing phantom move/insert dispatches and isDragging flapping that grow worse the longer the editor stays open.

12.3 The fix (applied)

Two changes, both in the fork

1 · lib/dnd/recover-drag-operation.ts new

recoverDragOperation(manager) forces a wedged operation back to idle by doing what the interrupted cleanup() would have done:

  • set source.status = "idle" — the signal dnd-kit's own stop() is blocked on, so its normal teardown gets a chance to run first;
  • if that didn't take (aborted controller), clear operation.controller and call operation.reset() directly — this flips status.initialized false, which is what makes the Cursor plugin drop its grabbing stylesheet;
  • in both the host document and the canvas iframe: strip [data-dnd-dragging], [data-dnd-dropping], the popover attribute and the --dnd-* custom properties from the stranded element, and remove the leftover [data-dnd-placeholder] clone.

2 · components/DragDropContext/index.tsx — watchdog + effect-leak fix

let dispose: (() => void) | undefined;
let watchdog: ReturnType<typeof setTimeout> | undefined;
let settled = false;

const settle = () => {
  if (settled) return;                 // idempotent — fixes the double-fire
  settled = true;
  if (watchdog !== undefined) clearTimeout(watchdog);
  dispose?.();                         // hoisted, so this actually disposes
  onAnimationEnd();
};

dispose = effect(() => {
  if (source.status === "idle") settle();
});

if (!settled) {
  watchdog = setTimeout(() => {
    if (recoverDragOperation(manager)) {
      console.warn("[puck] Drop never completed; forced the drag operation back to idle. …");
    }
    settle();                          // still applies the user's edit
  }, DROP_WATCHDOG_MS);                // 1500ms — drop animation is 250ms
}

Why 1500 ms: the drop animation is duration: moved ? 250 : 0 and is scheduled behind manager.renderer.rendering, so a healthy drop settles far inside a second. 1500 ms leaves generous headroom on a slow machine while keeping the recovery imperceptible. The settled flag guarantees the happy path is never affected — the watchdog is cleared the instant the real signal arrives.

Crucially, the watchdog still calls settle(), so the user's edit is applied even on the recovery path. The drop is not lost; it just completes without the animation.

Residual risk (worth knowing)

The watchdog is armed from dragend. If an operation were ever to wedge before dragend is dispatched (stuck at initializing), nothing arms it. That path has not been observed and no code path in the fork produces it, but if the freeze ever recurs without the [puck] warning in the console, that is where to look next — the fix would be a pointerup-based net in use-sensors.ts.

12.4 How to verify

Automated

lib/dnd/__tests__/recover-drag-operation.spec.ts — 4 tests covering: healthy operation untouched; stranded dropped/dropping forced to idle; recovery with a destroyed draggable; DOM restoration of the stranded feedback element and placeholder. All pass. Full suite: 377 passing, unchanged from baseline (one suite fails to load both before and after — see §14.1).

Manual, in the browser

  1. Open Design Studio and drag blocks around for a few minutes, including into and out of nested Sections and shell zones.
  2. Watch the console. The fix is working if you see [puck] Drop never completed; forced the drag operation back to idle — that is a freeze that was caught and repaired. Zero occurrences means no wedge happened.
  3. The bug is gone if you never again see a permanently-grabbing cursor, and never see Cannot start a drag operation while another is active.

Note: this could not be exercised in-session — the Browser pane renders the editor without requestAnimationFrame/screenshots, so drop animations don't run there. The static chain above is traced line-by-line through the installed dnd-kit 0.1.18 sources, and the recovery logic is unit-tested; the end-to-end confirmation is yours to make.

13. Code smells & bad patterns

13.1 critical Type checking is disabled

apps/web/next.config.mjs and apps/store/next.config.ts both set typescript: { ignoreBuildErrors: true }. Running tsc --noEmit -p apps/web/tsconfig.json today reports 648 errors. Separately, the fork's own packages/editor-packages/core/tsconfig.json cannot resolve @workspace/ui/* or @/core at all (wrong moduleResolution), so the package is not independently type-checkable. There are also 66 as any casts in the editor.

13.2 critical Unbounded module-level caches

WhereProblem
lib/resolve-component-data.ts:14export const cache = { lastChange: {} } — keyed by component id, never evicted. Every block ever resolved (including deleted ones, across page switches) retains a full copy of its props for the life of the tab.
store/index.ts:203, 226, 232Key mismatch. The timeout is stored as pendingLoadTimeouts[id] but deleted as delete pendingLoadTimeouts[loadId]. The delete never matches, so the map grows without bound and concurrent loads on the same id silently overwrite each other's handles.
DropZone/index.tsx:585-590zoneStore.enabledIndex gains an entry per zone on mount but no entry is ever removed on unmount. Every page switch adds more; every DraggableComponent subscribes to this store.
lib/use-hotkey.ts:174-185useHotkey writes a trigger into a module-level zustand store and never unregisters on unmount. Callbacks with stale closures survive the component that created them.

13.3 high The barrel cycle

components/AutoField/fields/ArrayField/index.tsx:33 does import { setDeep } from "../../../../bundle" — a core UI component importing the package's own public entry point. That barrel re-exports config/index.tsx, which eagerly imports all 62 blocks. Meanwhile ~10 files under config/blocks/ and config/plugins/ import types from @/core, closing the loop the other way. This is what makes one jest suite fail to even load, and what makes every edit recompile everything. Fix: import setDeep from lib/data/set-deep directly, and switch config/** to deep type imports.

13.4 high Duplicated storefront code across apps

See §15.3 — 16 byte-identical files. This is the highest-churn correctness risk in the repo: a fix applied to one copy leaves the other broken.

13.5 medium Imperative DOM escape hatches

DraggableComponent reaches around React in several places: it mutates el.style.position, sets/removes data-puck-* attributes by hand (:624-637), registers imperative sync()/showOverlay() methods into the store, and mutates sortable.droppable.disabled directly from an effect (:253-273). Each is defensible in isolation; together they mean component state and DOM state can diverge, and there is no single place to reason about "is this block draggable right now".

13.6 medium Debug scaffolding left in shipped code

const DEBUG = false / RENDER_DEBUG = false constants gate dead branches in DragDropContext, DraggableComponent and DropZone (including a getRandomColor() helper that only ever runs when RENDER_DEBUG is flipped). 11 console.log calls remain in lib/migrate.ts, components/AutoFrame and lib/plugin-debug.tsx.

13.7 medium Timing constants as coordination

The DnD path coordinates itself with hand-tuned delays rather than state: AREA_CHANGE_DEBOUNCE_MS = 100, tempDisableFallback(100), setTimeout(forceUpdate, 50) (DragDropContext:190-195), throttle(handleMove, 50) (NestedDroppablePlugin:274), and the nested 100 ms/200 ms pair in use-min-empty-height. A comment at DragDropContext:269 even concedes "we always cancel the debounce if the params change, so we could just use a timer". These are mostly inherited from upstream, but they are why zone switching feels non-deterministic under load.

13.8 low Stale deprecation still wired up

DropZone/index.tsx:488-496 warns that DropZones are deprecated in favour of slot fields and links to a Puck migration guide. lib/migrate.ts implements that migration but is not run anywhere. Either run it once over the fixtures and delete both, or drop the warning.

13.9 high Bilingual migration is not idempotent for default-only props

In normalizeComponentNode / root normalise, order is: 

migrateRenamedProps → migrateBilingualTextProps → mergeDefaults → …

A prop that exists only in defaultProps (never on the saved payload) is therefore filled in after the bilingual pass, so it stays a plain string on the first normalise. The second normalise then sees the string and converts it to { ar, en }. Consequence: normalizeEditorData(normalizeEditorData(x)) ≠ normalizeEditorData(x) for root shell defaults like drawerTitle, drawerTriggerLabel, footerTagline, and for block defaults like ButtonGroup.allButtonTitle.

site-data-fixtures.spec.ts (idempotency), site-data-mobile.spec.ts, mobile-sync.spec.ts and storefront-mode.spec.ts currently fail for exactly this reason — they assert bare strings against values that the migration rewrote. bilingual-migration.spec.ts itself is written against Vitest while the package runs Jest, so it never loads.

Fix: either (a) run bilingual migration again after mergeDefaults, or (b) ship all bilingual defaultProps as already- shaped { ar, en } objects and teach the tests to expect that. Prefer (b) for newly converted blocks; (a) is the durable fix for anything still defaulting as a string. Tracked in §16, Phase G.

14. Performance

14.1 critical Eager block imports + transpilePackages

config/index.tsx:1-58 statically imports all 62 blocks. Combined with transpilePackages: ["@puckeditor/core"] in both apps and the barrel cycle above, every edit to any block recompiles the entire editor, and every consumer of @/core — including apps/store's storefront pages — pulls the whole registry into its bundle. Leaflet, TipTap and Embla all ride along.

Fix: break the cycle (§13.3) first, then make the registry lazy — components: { Section: () => import("./blocks/Section") } resolved at render — or at minimum split the 9 // IGNORED blocks out.

14.2 high Per-frame rAF position polling

DraggableComponent/index.tsx:384-409. While any block's overlay is visible (hover or selection), a requestAnimationFrame loop calls getBoundingClientRect() every frame, forever, and triggers a React setState whenever the element moved. It runs for the hovered block and the selected block simultaneously, inside the iframe, and never stops while the selection persists.

Fix: replace with a PositionObserver/IntersectionObserver pair, or at minimum gate the loop off while ui.isDragging is true — which also removes one of the freeze amplifiers from §12.2.

14.3 high elementsFromPoint on every pointermove

NestedDroppablePlugin.ts:250-282 installs a capture-phase pointermove listener on document.body that runs document.elementsFromPoint() and then frame.elementsFromPoint(), iterates every hit element, and calls getBoundingClientRect() on each candidate. Throttled to 50 ms — so up to 20×/s during a drag, each pass forcing synchronous layout in two documents.

Fix: cache the frame lookup (getFrame() runs a querySelector per call), bail early when the pointer hasn't crossed an element boundary, and cache bounding boxes for the duration of a drag.

14.4 medium normalizeSiteData deep-clones the tree

config/lib/normalize-editor-data.ts:43-47 uses structuredClone (good — the recursive fallback is ~10× slower), but it still clones the entire site on every call, and site-data.ts:510 does a JSON.parse(JSON.stringify(...)) of the whole desktop site for the mobile fork. Neither belongs in a hot path — audit the call sites.

14.5 medium localStorage on the render path

97 localStorage call sites across the editor and both apps. site-data.ts parses the full site JSON synchronously on every readSiteData(), and several hooks call it inside render or in a storage-event handler. Memoise per mode and invalidate on write.
